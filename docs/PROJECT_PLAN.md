# Retailrocket 用户增长运营项目总计划

## 1. 目标与成功标准

### 1.1 求职目标

将 Retailrocket 全量电商行为数据建设成一个可复现、可在线演示、可在面试中完整讲述的用户增长/产品运营作品集，证明以下能力：

- SQL 数据建模和指标口径设计；
- Python 自动化、数据质量和统计分析；
- 漏斗、留存、复购、生命周期和品类机会分析；
- 从真实发现形成用户分群、运营动作与实验验证方案；
- Git、GitHub、Pull Request、CI 和 Release 的工程化协作能力。

### 1.2 核心业务问题

1. `view → addtocart → transaction` 的最大流失发生在哪里？
2. 哪些首个会话行为与更高的 D7/D14 留存或购买意愿相关？
3. 哪些品类规模较大、购买意向较高，却存在明显转化缺口？

预登记假设：

- H1：首次会话“加购未购买”访客的 D7 活跃留存率，比“仅浏览”访客高至少 5 个百分点。
- H2：严格有序漏斗中存在一个步骤贡献超过 60% 的流失会话。
- H3：至少一个达到样本门槛的品类，其浏览到购买转化率比同级品类基准低至少 2 个百分点。

未达到阈值时必须报告“假设未得到数据支持”，不能筛选或修改口径制造结论。

### 1.3 完成标准

- 全量 CSV 可通过显式 Schema 自动构建 DuckDB。
- 核心指标可由一个 Python CLI 命令重算并通过精确 Fixture 测试。
- 漏斗检查事件顺序，留存处理观察窗口，商品属性不存在未来泄漏。
- 看板至少形成三条真实运营故事，每条包含发现、意义、动作和验证方案。
- 真实和模拟数据在数据库、导出、看板及文字结论中完全区分。
- GitHub 不包含完整数据、数据库、凭证或大型临时文件。
- 六个版本都有清晰的提交、PR、标签、Release、验证证据和变更记录。
- `v1.0.0` 支持 Demo 模式运行，在线演示可访问，求职材料可直接使用。

- 代码通过 `PRODUCT_OPS_DATA_HOME`/配置解析路径，不把本机用户名写入业务逻辑。

### 2.2 数据范围

- `events.csv`：预期 2,756,101 条事件。
- 两份 `item_properties`：预期合计 20,275,902 条属性历史，完整导入。
- `category_tree.csv`：预期 1,669 条分类关系。
- `outputs/retailrocket_sample/`、`tools/build_retailrocket_sample.py`、`tools/build_retailrocket_workbook.mjs` 及桌面小样例只用于教学、理解字段和演示格式，绝不用于正式指标、正式看板或业务结论；这些现有资产必须保留，不删除。
- 原始数据不删除、不重写、不上传 GitHub；公开仓库仅包含代码、文档、小型 Fixture、聚合结果和少量截图。

### 2.3 数据分层

使用一个 DuckDB、五个 Schema：

| Schema | 职责 |
|---|---|
| `meta` | 文件 Hash、大小、导入时间、代码版本和运行记录 |
| `raw` | 保留字段值的原始表 |
| `stg` | 显式类型、UTC 时间、事件枚举和质量标记 |
| `core` | 事件、会话、交易、商品属性历史和分类维度 |
| `mart` | 看板和报告使用的运营指标集市 |

关键口径：

- 相邻事件间隔严格大于 30 分钟时开启新会话；
- 订单数为唯一 `transactionid`，商品交易事件数另行保留；
- 商品属性整理为 `[valid_from, valid_to)` 区间，事件关联当时有效属性；
- 仅解释 `categoryid`、`available`，其余匿名属性只保存和用于不带语义的质量/变化分析；
- SQL 是指标公式唯一来源，Python 负责流程、验证、统计和导出；
- Streamlit 只读取 `mart` 或小型聚合文件。

### 2.4 真实与模拟边界

真实 Retailrocket 数据没有注册、金额、成本、渠道或实验分组。`v0.1.0` 至 `v0.4.0` 不计算真实 GMV、AOV、CAC、ROAS 或 LTV。`v0.5.0` 的渠道与实验数据必须：

- 使用独立表和固定随机种子；
- 不复用真实 `visitorid`；
- 全链路设置 `data_origin='synthetic'`；
- 在数据库、文件、图表和文档中标注“模拟数据 / SIMULATED”；
- 不作为真实业务提升证据。

### 2.5 统一 CLI

目标接口：

```text
python -m product_ops.cli ingest
python -m product_ops.cli build
python -m product_ops.cli metrics
python -m product_ops.cli validate
python -m product_ops.cli export
python -m product_ops.cli run-all
```

## 4. Goal 2 / v0.2.0：全量 DuckDB 数据仓库

### 目标

将完整 CSV 导入 DuckDB，建立可幂等重建的 SQL 分层模型。

### 实施步骤

1. 检查 D 盘可用空间，准备 `warehouse`、`parquet`、`tmp`、`exports`。
2. 创建文件清单：路径、大小、Hash、修改时间、导入时间和代码提交号。
3. 使用显式字段类型导入全部事件、商品属性和分类关系。
4. 建立 `meta/raw/stg/core/mart` Schema，不依赖 CSV 自动类型推断。
5. 统一毫秒时间戳为 UTC，并保留原始时间戳。
6. 建立 `core.fct_event`，保留原始事件和质量标记。
7. 使用 30 分钟规则建立 `core.fct_session`。
8. 建立按唯一 `transactionid` 聚合的 `core.fct_transaction`。
9. 合并两份完整属性文件；建立属性历史和 `categoryid`、`available` SCD2 区间。
10. 使用 ASOF 逻辑关联事件发生时有效的商品属性，禁止未来泄漏。
11. 递归建立分类深度、根分类和路径，检测环、孤儿和缺失父节点。
12. 对复杂 SQL 执行 `EXPLAIN ANALYZE`，完成行数、覆盖率、边界和幂等性测试。

### 验收

- 原始表行数与 CSV 一致，两份匿名属性完整保存。
- DuckDB 和临时目录全部位于 D 盘。
- 29/30/31 分钟会话边界测试通过。
- 属性关联不存在未来信息泄漏。
- 分类异常、未知事件、空值和交易异常有质量报告。
- 连续两次构建不会产生重复数据，结果一致。
- `v0.2.0` PR、CI、标签和 Release 完成，Release 包含数据模型与质量摘要。

### 用户评审/授权点

仅在 D 盘空间不足 5 GB、行数与数据契约冲突或真实异常需要修改核心口径时请求业务决定；Git/GitHub 各写操作仍逐步授权。

## 5. Goal 3 / v0.3.0：Python 自动运营指标引擎

### 目标

由 Python CLI 自动执行版本化 SQL，计算真实运营指标并输出可验证快照。

### 实施步骤

1. 建立指标注册表和指标字典，以 SQL 为唯一公式来源。
2. 活跃：DAU、滚动 7 日 WAU、滚动 30 日 MAU、DAU/MAU、首次观察和回访访客。
3. 会话：会话数、事件/会话、商品/会话、时长中位数和 P75。
4. 漏斗：行为覆盖、严格有序会话、同商品严格有序三套口径。
5. 路径：主流路径、步骤耗时、无前序交易和顺序异常。
6. 留存：D1/D3/D7/D14/D30 活跃留存和周 Cohort，正确处理右截断。
7. 交易：购买访客率、唯一交易数、每交易不同商品数、复购率和复购间隔。
8. 生命周期：首次跳失、活跃浏览、加购未购、首次购买、重复购买、流失风险。
9. 商品/品类：规模、转化率、Wilson 95% 区间和达到样本门槛后的机会指标。
10. 数据质量：属性覆盖、分类关联、空值、未知事件和异常访客。
11. Python 自动输出 `mart`、CSV/Parquet、质量 JSON、Markdown 摘要和运行清单。
12. 使用确定性 Fixture 验证精确公式，并检验三项预登记假设。

### 验收

- `run-all` 可重建数据并刷新全部指标。
- SQL Mart、Python 导出与测试期望值一致。
- 留存分母只包含完整观察窗口 Cohort；总体留存按用户数加权。
- 漏斗检查先后顺序，交易事件与订单数不混淆。
- 每项指标都有业务问题、公式、粒度、时间窗、来源和限制。
- 三项假设均输出“支持/不支持”和证据，不只挑选正向结果。
- `v0.3.0` PR、CI、标签和 Release 完成。

### 用户评审点

展示三条真实发现，让用户决定求职叙事更偏用户运营、增长运营或电商运营；默认采用样本充分、效应明显且动作可落地的一条作为 README 主故事。

## 9. 跨版本 Git 与沟通流程

每个里程碑采用：

```text
Issue → feat/fix 分支 → 实现与测试 → 显式 stage → commit → push
→ Draft PR → CI → merge → SemVer tag → GitHub Release
```

固定规则：

- 每个里程碑一个主要 PR；完整工作单元可以有多个小提交。
- 禁止 `git add .`、`git add -A`、`git add --all`，只能显式列出文件。
- 安装依赖、登录、建仓库、stage、commit、push、PR、merge、tag、Release 和公开部署分别请求授权。
- 每个检查点按“已完成、验证结果、当前风险、下一步、需要决定”汇报。
- 发现许可风险、口径冲突、空间不足、数据异常或会改变求职叙事的方案时，先询问用户。
- 普通代码组织、测试补充和性能优化按 `AGENTS.md` 推进，并记录在 `docs/PROGRESS.md`。

## 10. 执行建议

- 一个 Codex Goal 只对应一个里程碑和一个 Release，不同时启动六个里程碑。
- 不因数据约 1 GB 就抽样核心事件或删除匿名属性；DuckDB 和临时文件放 D 盘，并保留轻量 Demo 作为展示层方案。
- 先保证 SQL 口径、质量和复现，再做视觉效果；暂不优先做机器学习。
- 求职价值排序：真实业务问题与行动闭环 > 指标口径与验证 > 工程规范 > 技术数量。
- 每版都必须可运行、可测试、可解释；Release 是稳定检查点，不是进度截图。
